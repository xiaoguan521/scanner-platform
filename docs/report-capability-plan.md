## 2. 端口发现策略

### 2.1 端口范围(新建扫描时选择)

| 选项 | 说明 | 默认 |
|---|---|---|
| 常见端口 | 内置清单,覆盖常见服务和中间件端口,清单可配置 | **默认** |
| 自定义 | 手工输入端口或范围,如 `22,80,8000-8100` | |
| 已登记端口 | 仅扫描资产里已有的端口 | |
| 全端口(1–65535) | 耗时长、请求量大。**必须二次确认**,提示预计耗时和对目标的影响,并写审计 | |

> 参考报告在一台服务器上发现了 30 个开放端口,其中不少是非标准端口(如 7777、8118、18888)。只用很小的"常见端口"清单会漏掉这类服务,所以内置清单要覆盖主流中间件,必要时让用户选择"全端口"。

### 2.2 排除端口

- 格式:单个端口、范围、逗号分隔,例如 `3306,9000-9100`;校验范围 1–65535,格式错误时给出明确提示。
- **三个层级**:系统默认(初始为空)、资产级(资产详情里把端口标记为"排除")、任务级(创建扫描时填写)。三者取并集。
- **优先级最高**:被排除的端口**不发起任何网络连接**,包括存活探测、端口扫描、服务识别和漏洞检测。
- 报告和任务详情里列出"本次已排除端口"清单,并写入审计日志。

### 2.3 强度与速率

沿用"温和 / 标准 / 积极"三档,由后端映射为:每目标并发连接数、每秒请求数、超时时间。选择全端口时,默认使用"温和"。

### 2.4 存活检测

对输入的 IP 先做存活检测,不存活的目标标记为"未存活",不再做后续步骤。报告综述里的"存活资产数"来自这里。

### 2.5 Nginx 四层代理保护(运维要求)

- 端口发现阶段对每个"IP:端口"只做必要的 TCP 连接和有限的协议识别探测,**每个端口的探测次数有上限**(默认 3 次),不重复探测。
- 出现"连接可建立但无响应、立即复位、响应特征与已登记资产不符"等情况,判定为**疑似转发**:写入 `port_quarantine`,之后只保留"端口开放"信息,**不再挂载 Web 或漏洞检测模板**,并在后续任务里直接跳过,直到人工解除。
- **排除端口优先于一切判断**。
- 判断阈值可配置,不作为唯一依据。

### 2.6 范围围栏(保持不变)

- 目标清单永远是用户输入的 IP 集合。
- 服务识别、Web 请求的重定向只允许在同一主机内,不得连接到其他 IP。
- 每个任务记录实际探测过的 IP、端口范围、排除端口,写入审计。

## 3. 弱口令处理(D2)

1. 第一阶段**不实现**任何口令猜测、爆破、默认口令登录尝试。注意:"默认口令"检测模板本质上也会尝试登录,同样不启用。"未授权访问"检测(如某服务无需认证即可访问)不属于口令猜测,可以保留。
2. 建立**检测能力注册表**,每项检测能力有状态:

| 能力 | 第一阶段状态 |
|---|---|
| 系统漏洞 | 已启用 |
| Web 漏洞 | 已启用 |
| 登录入口发现 | 已启用 |
| 弱口令 | **未启用** |
| 基线检查 | 未提供(后期) |

3. 界面和报告按能力状态展示:
   - 总览卡片、统计表、报告章节中,未启用的能力显示"**本次未启用该检测项**",灰色样式,**不显示数字 0**。
   - Excel 的"弱口令详情"工作表保留,但内容写一行"未启用该检测项"。
   - "漏洞总数"的统计口径不含未启用的类型。
4. 数据模型里预留 `weak_credential` 类型。将来启用前必须单独评审:授权、限速、账号锁定风险、字典管理、审计。

## 4. 数据模型增补

> 以下是字段清单,具体表结构由 Codex 设计,须兼容 SQLite 与 PostgreSQL。

### 4.1 资产

名称、是否核心、业务组、责任人、所属部门、联系电话、MAC 地址、操作系统(名称与族)、设备类型、设备小类、厂商、型号、是否存活、最近存活时间。

### 4.2 资产服务(端口)

资产、端口、协议、状态、服务名、软件名与版本、中间件、开发语言、开发框架、数据库、应用或服务、网站 URL、网站标题、是否 TLS、首次与最近发现时间、是否被排除。

### 4.3 发现项(在现有基础上增加)

| 字段 | 说明 |
|---|---|
| `risk_type` | 系统漏洞 / Web 漏洞 / 弱口令(预留)/ 登录入口 |
| `detect_method` | **原理验证** / **版本推断** / **配置检查** |
| `confidence` | 高 / 中 / 低 |
| `cvss_score` | 0–10 风险值,严重度按分级标准由它推导 |
| `vuln_category` | 统一的漏洞类型分类(见 4.5) |
| `identifiers` | 平台编号、CVE、CNNVD、CNVD、Bugtraq(JSON) |
| 中文内容 | 风险描述、风险影响、解决方案、参考资料 |
| `evidence` | 风险举证(原理验证存请求和响应摘要;版本推断存"组件:版本"和匹配规则) |
| `port`、`component` | 风险端口;识别出的组件名与版本 |

### 4.4 登录入口

资产、类型(系统登录入口 / Web 登录入口)、名称、端口、URL、是否启用 HTTPS、是否有验证码、是否有防爆破机制(未知时为空)、举证。

### 4.5 漏洞知识库与分类字典

- **漏洞知识库**:平台编号、各类外部编号、中文标题、描述、影响、解决方案、参考资料、风险值、分类、受影响的组件与版本范围、来源、更新时间。
- **分类字典**:参考报告有 32 类(信息泄露、拒绝服务、配置不当、未授权访问、跨站脚本、绕过认证、代码注入等),建立自己的字典,并尽量映射到 CWE。

### 4.6 报告

- **报告**:名称、模板、范围(任务 / 资产 / 业务组 / 时间)、格式、状态(生成中 / 就绪 / 失败)、文件路径与大小、创建人、创建时间、**数据快照版本**。
- **报告模板**:公司名称、Logo、页眉页脚、评定标准文本、安全建议文本、章节开关。

## 5. 检测方式与置信度(比参考产品做得更清楚)

参考报告里,系统漏洞占 69%,其中大量是"识别到版本 → 查表得出 CVE",风险举证只有"jetty:9.2.z"这类版本号;只有约 46% 的条目标注为"原理扫描"(实际验证过)。我们要把这个区别明示出来。

| 检测方式 | 含义 | 默认置信度 |
|---|---|---|
| 原理验证 | 实际发送请求并确认了漏洞特征 | 高 |
| 配置检查 | 确定性的配置判断(如缺少安全响应头、方法启用) | 高 |
| 版本推断 | 仅根据识别到的版本匹配漏洞库,**未验证** | 中或低 |

- 界面:每条发现带检测方式标签,可筛选,统计里可以单独看"仅已验证"。
- 报告:详情里单独一行"检测方式";综述里说明其中有多少条为版本推断。
- 对操作系统层面的组件(如 OpenSSH),发行版常通过打补丁而不改版本号,远程版本推断误报多,**默认置信度低**,并提示"建议登录主机核查,或使用主机本地扫描"。

## 6. 系统漏洞版本匹配模块(新增)

流程:`服务识别 → 组件 + 版本 → 漏洞知识库匹配 → 生成发现项(版本推断)`。

- 需要一个"组件识别"层,把服务横幅、HTTP 响应特征、页面标题等转成"组件名 + 版本"。
- 漏洞知识库按受影响的版本范围匹配。
- Nuclei 的原理验证结果,如果知识库里有对应条目,就补全中文内容和编号;没有时使用模板自带元数据,并标记"内容为原文,待中文化"。
- 数据来源:先用公开的漏洞数据加自建中文内容;中文化可以用 AI 辅助,但必须人工抽检(后期)。CNNVD、CNVD 等数据待法务确认(D3)。
- 端口扫描、服务识别要使用哪些开源工具,需要先核对许可证(例如 Nmap 的许可证对再分发有限制,我印象里需要法务确认;同生态的 naabu、httpx 可以评估,但我没有核实其许可证)。

## 7. 报告能力规格

### 7.1 格式

| 格式 | 阶段 |
|---|---|
| Excel(多工作表) | 第一批 |
| HTML(单文件、离线可看) | 第一批 |
| Word(docx) | 第二批 |
| PDF | 后期 |

### 7.2 Word 报告章节(对照参考报告)

1. **封面**:公司名称或 Logo、报告标题、生成时间。
2. **综述**:总体安全等级、存活资产与风险资产数、漏洞数(含分级)、弱口令(未启用)、登录入口数;注明其中版本推断的条数。
3. **资产统计**:
   - 资产基本信息(设备类型分布、操作系统 TOP5 图;资产表)。
   - 资产端口信息(端口 TOP5 图;端口表:IP、端口数、端口、协议、服务、软件)。
   - 本次已排除的端口清单。
4. **资产风险信息**:漏洞、弱口令(未启用)、登录入口的各资产汇总表。
5. **资产详情**:每台资产一节:基本信息、端口信息(含网站 URL 和标题)、风险类型分布表。
6. **风险统计**:系统漏洞、Web 漏洞、弱口令(未启用)、登录入口四部分,每部分含:等级分布、影响资产 TOP5、出现次数 TOP5、TOP100 表格、类别统计。
7. **风险详情**:每台资产下逐条漏洞卡片,字段:风险等级、平台编号、CVE、CNNVD、CNVD、Bugtraq、风险端口、风险描述、风险影响、解决方案、**检测方式**、风险举证。
8. **附录**:单一系统漏洞、单一 Web 漏洞、单一资产的风险等级评定标准;安全建议(模板可配置)。

### 7.3 Excel 工作表

综述、资产风险统计、漏洞影响统计、主机资产详情、网站资产详情、漏洞详情、弱口令详情(未启用说明)、登录入口详情。漏洞详情需含"检测方式""置信度"列。

### 7.4 规模与性能

- **异步生成**:报告通过后台任务生成,界面显示进度,失败可重试。
- **TOP100 截断**:表格只展示前 100 项,每个漏洞最多列出 10 个影响资产,文末注明"更多信息请在平台查看或下载 Excel"。
- 大报告流式写入,避免占用过多内存;设置文件大小上限提示。
- 图表由服务端生成图片,不依赖浏览器。
- 报告生成时**冻结数据快照**,避免生成之后数据变化导致前后不一致。

### 7.5 统计口径与等级规则

- **漏洞总数** = 系统漏洞 + Web 漏洞(启用弱口令后再加上弱口令)。**登录入口单独统计**,不并入漏洞总数。不要使用含义含混的"风险总数"。参考报告里资产表是 240、资产详情是 241(含登录入口),就是口径不统一的例子。
- **风险值与等级**:9–10 严重、7–<9 高危、4–<7 中危、0–<4 低危。
- **资产或总体等级**:取范围内最高的漏洞等级,顺序为 严重 > 高危 > 中危 > 低危 > 安全。评定标准表必须包含"严重"(参考报告的标准表里没有,但实际出现了)。
- 报告综述的数字必须与明细汇总一致,有自动化测试。
- 报告命名:`{首个目标}等{N}个目标_{方案名}_{时间戳}`。

## 8. 给 Codex 的执行顺序

每一步都在 `main` 上小步提交,并在结束时给出"演示脚本"(我点哪里、该看到什么)。

| 步骤 | 内容 | 你会看到什么 |
|---|---|---|
| **R1 数据模型与口径** | 4 章的字段与迁移;检测能力注册表;等级与口径规则;分类字典 | 种子数据里的发现项带检测方式、置信度;未启用的能力显示"未启用"而不是 0 |
| **R2 端口发现与服务识别** | 存活检测、端口发现、服务识别、排除端口、强度、四层代理保护;向导里的"端口范围"和"排除端口"输入 | 输入一个靶机 IP,选择常见端口,排除一个端口,结果里看到端口列表,被排除的端口没有任何连接 |
| **R3 资产画像与登录入口** | 操作系统、设备类型、技术栈识别;登录入口发现及属性 | 资产详情页显示完整画像和登录入口 |
| **R4 漏洞知识库与版本匹配** | 知识库、组件识别、版本匹配、检测方式标注 | 对靶机得到带中文说明的系统漏洞,标注"版本推断" |
| **R5 Web 配置类检查补齐** | 安全响应头、CORS、方法启用、默认页面、常见未授权接口等 | Web 漏洞数量和类别接近参考报告的水平 |
| **R6 报告引擎** | Excel 与 HTML,再做 Word;图表、TOP100、数据快照、异步生成 | 一键生成报告并下载 |

### 验收方式

用**实验靶机**(不是真实内网)扫描后生成报告,对照本文第 7 章的章节清单逐项自检,把结果写到 `docs/product/report-checklist.md`(只记录章节和字段是否具备,不含任何真实数据)。

### 验收标准

- 被排除的端口不产生任何网络连接(抓包验证)。
- 弱口令相关位置全部显示"未启用",没有出现"0 个"。
- 每条发现都有检测方式和置信度;版本推断的条目在界面和报告中都能被区分。
- 综述数字与明细汇总一致(自动化测试)。
- 同一份数据导出的 Excel、HTML、Word 内容一致。
