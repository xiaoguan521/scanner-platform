## 9. PR 与范围纪律

### 9.1 硬规则

28. **一个 PR 只做一个任务**,任务编号对应 `dev-plan-daily.md` 中的某一天或某个 PoC。计划之外的工作不得顺手实现:发现需要时,在汇报中提出,由人工决定是否排入计划。
29. **安全关键目录的改动不得与其他目录的改动混在同一个 PR 里**。安全关键目录见第 8.3 节,至少包括 `internal/versionmgr`、`internal/scope`、`cmd/worker`、`internal/executor`、`internal/scheduler` 中的租约代码。
30. **PR 描述必须与实际 diff 一致**。每次向 PR 追加提交后,必须同步更新描述、验证记录和"未验证"清单。描述里不得出现与代码状态相反的说法(例如代码已存在却写"尚未实现")。
31. 不得直接推送到 `main`;不得自行合并涉及安全关键目录的 PR;不得对已被评审过的分支强制推送(`force push`),确需改写历史时先说明并等待人工同意。
32. 分支命名:`feat/<poc编号或Day编号>-<简短名称>`、`fix/...`、`docs/...`、`ci/...`。

### 9.2 规模参考

- 单个 PR 建议不超过约 15 个文件或约 400 行非生成代码。超出时先考虑拆分。
- 生成的文件(如 `package-lock.json`)不计入行数,但要在描述里单独说明。

### 9.3 PR 描述必须包含的内容

```markdown
## 任务
对应计划:Day N / PoC #X,一句话说明目标。

## 变更摘要
(必须与 diff 一致。按目录列出实际改动,不得遗漏前端、CI、脚手架等附带内容。)

## 涉及的 AGENTS.md 硬规则条目
(列出条目编号。)

## 已验证(命令 + 结果摘要)
- make build:
- make lint:
- make test(含 -race):
- 本任务验收命令:

## 未验证 / 尚未实现
(逐条列出,不得省略。)

## 需要人工重点评审的位置
(文件:行号,以及为什么。)

## 与计划的偏差
(没有则写"无"。)

## 是否包含计划外内容
(必须填写"否",或逐项说明并给出理由。)
```

### 9.4 Draft 转 Ready 的条件

- CI 全部通过。
- 描述与 diff 一致,"未验证"清单完整。
- 涉及安全关键目录时,已列出评审重点。
- 不包含计划外内容,或已获人工确认保留。

## 10. 前端(`web/`)与 npm 依赖

### 10.1 硬规则

33. **离线可用**:前端不得从 CDN 加载脚本、样式或字体,所有资源必须随构建产物一起打包。
34. **新增 npm 依赖需要说明用途和许可证**,版本固定,并提交 `package-lock.json`。默认允许 MIT、Apache-2.0、BSD、ISC;其他许可证需先经人工批准。依赖更新单独提 PR,不与功能混合。
35. CI 与本地统一使用 `npm ci`,不使用 `npm install`(会改写锁文件)。CI 中应禁用依赖的安装脚本(如 `--ignore-scripts`),确需运行的脚本需单独说明并获批准。
36. **令牌、会话、凭据不得写入前端代码,也不得存入 `localStorage`**,除非已经过会话设计评审。认证与会话方案由 Server 端设计决定,不由前端自行实现。
37. **演示模式与 Server 模式必须严格区分**:
    - 演示数据只能来自 `web/src/mock`,且不得包含任何真实资产、IP、域名、人员信息。
    - Server 模式在接口不可用(501、网络错误)时必须显示"不可用",**不得回退到 mock 数据**,不得构造任务成功、扫描成功、已修复等状态。
    - 所有会产生实际后果的操作按钮(创建任务、审批、停止、回滚、状态变更)在后端具备授权、审计与服务端决策能力之前保持禁用。
    - 页面不得暗示围栏已生效、引擎已运行、规则包已验签,除非数据来自 Server 并有对应证据。
38. **前端类型与 OpenAPI 同步**:在引入经评审的代码生成工具之前,任何对 `docs/api/openapi.yaml`、`internal/api/dto.go`、`web/src/types` 的改动,必须在同一个 PR 中三者一并更新,并在描述中列出变更字段。
39. 前端依赖需纳入漏洞与许可证扫描(与 Go 依赖同级别),扫描结果不通过时不得合并。

### 10.2 范围提醒

前端属于 Phase 1 第 8 周的计划内容。Phase 0 期间只允许维护已有脚手架,**不得扩展新页面或新功能**,除非计划做了调整。

## 11. CI 与供应链

### 11.1 硬规则

40. GitHub Actions 中引用的第三方 Action **必须固定到提交哈希(SHA)**,并在行尾注释对应版本号,不得只写可变的版本标签或分支名。
41. 工作流默认使用最小权限:显式声明 `permissions`(通常为 `contents: read`),并设置 `persist-credentials: false`。需要更高权限的 Job 必须在 PR 里说明理由。
42. **不得使用 `pull_request_target` 处理来自不可信来源的代码**;不得在工作流中打印或回显密钥;未经任务要求不得新增使用 secrets 的步骤。
43. 发布产物必须附校验和。Release 仅创建 **Draft**,由人工审查后才能公开。普通 SHA-256 校验文件不等同于软件签名,代码签名与公证需单独设计与评审。
44. `.github/workflows/` 下的任何改动,都要在 PR 描述里逐项说明:改了什么、权限是否变化、是否引入新的第三方 Action。
45. 工作流的改动不得与功能代码混在同一个 PR 里(CI 脚手架的首次建立除外,需在描述中说明)。

## 12. 仓库与信息保密

### 12.1 硬规则

46. 仓库必须保持 **Private**。不得自行修改仓库可见性。
    - 当前任务临时例外(2026-10-16,人工明确授权):本次文档整理与 PR #1 拆分暂时继续使用 **Public**。本例外不授权改变仓库可见性,不放宽第 47–49 条的信息保密要求;何时恢复 Private 由人工决定。
47. 以下内容**不得提交**到仓库的任何文件、测试夹具、文档、日志或 PR 描述中:
    - 真实内部 IP、域名、网段、资产清单。
    - 人员姓名、账号、工单号。
    - 凭据、令牌、私钥、证书私钥。
    - 真实扫描结果、真实漏洞数据、Harbor 镜像样本清单。
    文档和测试统一使用示例地址段(`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`)和示例域名。
48. 如果发现已提交了上述内容,**立即停止其他工作并报告**,由人工决定处置方式(包括轮换凭据、是否需要清理历史)。不得自行改写历史来"掩盖"。
49. 不得把仓库内容、日志、报告或扫描数据发送到未经批准的外部服务。

## 13. 每日汇报模板

每个任务结束时,按以下模板汇报。**不得声称"已验证"而实际没有运行**,无法验证的内容必须写在"未能验证"里。

```markdown
## Day N 汇报
- 任务:
- PR / 提交:
- 完成项:
- 未完成项及原因:
- 验证证据(命令 + 输出摘要):
  - make build:
  - make lint:
  - make test(含 -race):
  - 本任务验收命令:
- 未能验证的内容:
- 涉及的 AGENTS.md 硬规则条目:
- 需要人工重点评审的位置(文件:行号):
- 偏离计划之处:
- 是否包含计划外内容:
- 需要人工决策的问题:
- 明日计划:
```
