# 产品化调整方案(交给 Codex 执行)

> 目标:把现在"功能堆在一起、没有章法"的框架,调整成**结构清晰、符合大厂安全产品习惯、新人不用培训就能上手**的平台。
> 本文件是 Codex 的执行依据。与 `AGENTS.md` 冲突时,以 `AGENTS.md` 的"早期开发模式"为准。

---

## 0. 给 Codex 的总说明

### 0.1 工作方式

- 在 `main` 上小步提交,每次提交都能编译、能运行。
- **先做第 7 章的 Stage 0(现状盘点),不改代码**,把结果写入 `docs/product/current-state.md`,再按 Stage 1 往后做。
- 每个 Stage 结束时,给出一份"演示脚本":我在浏览器里点哪几步、应该看到什么。
- 不确定的产品决策,先在 `docs/product/open-questions.md` 里记录并按本文件的默认值继续,不要停下来等。

### 0.2 三条底线(任何阶段都不能破)

1. 只扫描用户**明确输入**的 IP:端口,界面里不提供"扫描整个网段""发现主机"这类入口。
2. 不提交真实内部 IP、资产清单、密钥或扫描结果。
3. 不实现攻击、爆破、利用类功能。

### 0.3 本方案要解决的问题

| 现状问题 | 调整方向 |
|---|---|
| 功能入口散乱,不知道从哪开始 | 按"资产 → 扫描 → 漏洞 → 报告"一条主线重做导航 |
| 页面各写各的,风格和交互不统一 | 统一设计系统和通用组件 |
| 演示数据与真实数据两套通道 | 前端只保留一条真实 API 通道,演示靠种子数据 |
| 术语和状态各处不一致 | 统一枚举、统一文案、统一颜色 |
| 不好上手 | 首次使用引导、向导式新建扫描、空状态指引 |

## 1. 产品定位与角色

**一句话**:企业内部使用的漏洞扫描与漏洞管理平台,覆盖"发现 → 处置 → 复测 → 报告"闭环。

| 角色 | 主要诉求 | 权限 |
|---|---|---|
| 管理员 | 管用户、节点、规则库、系统设置 | 全部 |
| 安全工程师 | 建资产、发起扫描、处置漏洞、出报告 | 资产、扫描、漏洞、报告 |
| 审批人(运维负责人) | 批准扫描范围和时间窗 | 授权范围审批 |
| 只读用户 | 看总览和报告 | 只读 |

## 2. 信息架构(导航)

**一级导航固定为 6 项,顺序不变。未实现的模块不显示入口,不放空壳页面。**

```text
总览
资产
  ├─ 资产列表
  ├─ 业务组
  └─ 导入记录
扫描
  ├─ 扫描任务
  ├─ 定时计划
  └─ 扫描方案
漏洞
  └─ 漏洞列表(详情用右侧抽屉)
报告
  ├─ 生成报告
  └─ 历史报告
系统
  ├─ 用户与角色
  ├─ 节点管理
  ├─ 规则库
  ├─ 授权范围
  ├─ 审计日志
  └─ 系统设置
```

后期再加入的一级模块(现在**不要**出现在界面上):镜像仓库(Harbor)、主机本地扫描、基线与合规、AI 研判。

## 3. 核心用户旅程(所有设计以这三条为准)

### 旅程 1:首次使用(目标:10 分钟内看到第一份结果)

登录 → 总览页出现"快速开始"清单 → ① 添加第一个资产 → ② 选择扫描方案 → ③ 开始扫描 → ④ 查看结果。每完成一步自动打勾,全部完成后清单消失。

### 旅程 2:日常处置

总览看风险 → 点击数字下钻到漏洞列表(带好筛选条件)→ 点开漏洞看详情 → 指派、标记误报、接受风险或标记修复中 → 发起复测。

### 旅程 3:定时与报告

创建定时计划(选资产 + 方案 + 时间窗)→ 自动执行 → 在报告页生成并下载报告。

**可用性硬指标**:从登录到发起第一次扫描,不超过 **5 次点击**;任何列表页首屏加载不超过 **2 秒**(本地数据量 1 万条以内)。

## 4. 各模块的页面规格

### 4.1 总览

参考截图里的"攻击面总览"布局,但视觉自己设计,不照搬任何商业产品的外观。

| 区块 | 内容 |
|---|---|
| 顶部 | 风险评分(0–100)、有风险资产数、漏洞总数 |
| 等级分布 | 严重 / 高危 / 中危 / 低危 / 信息 |
| 趋势图 | 近 30 天漏洞总数,可切换 7 / 30 / 90 天 |
| TOP 5 | 风险最高的业务组、资产 |
| 待处置 | 未处理的严重和高危漏洞 |
| 最近任务 | 最近 5 个扫描任务及状态 |
| 系统状态 | 节点在线数、规则库版本与更新时间 |
| 快速开始 | 仅新用户显示 |

**规则**:所有数字都可点击,跳转到对应的筛选结果;总数必须等于各类之和(有自动化测试)。风险评分的算法写在 `docs/product/risk-score.md`。

### 4.2 资产

- **列表**:名称、地址、类型、业务组、负责人、已登记端口数、最近扫描时间、风险数。支持筛选、排序、批量操作、导出。
- **新增与导入**:单个新增;CSV 导入(提供模板下载),导入前先校验并给出"成功 X 条、失败 Y 条及原因"的报告,用户确认后才入库。
- **端口分类**:每个端口标记为 `Web` / `非 Web` / `跳过(如 Nginx 四层转发端口)`。未登记的端口不会被扫描。
- **详情页**:基本信息、端口与服务、漏洞、扫描历史。

### 4.3 扫描

**新建扫描(向导,4 步,不允许做成一个巨大的表单)**

| 步骤 | 内容 |
|---|---|
| 1 选目标 | 从资产选择,或手动输入"IP:端口"(实时校验格式)。**没有"整个网段"选项** |
| 2 选方案 | 预置方案卡片:快速检测、标准检测;每张卡片说明"检测什么、大约多久、对目标的影响" |
| 3 执行方式 | 立即执行 / 定时 / 仅在时间窗内执行;强度档位:温和、标准、积极(后端映射成引擎的速率和并发,**界面不出现引擎参数**) |
| 4 确认 | 摘要:目标数、端口、方案、强度、预计耗时、风险提示;勾选"我确认已获得授权",再点开始 |

**扫描任务列表**:状态、进度、目标数、发现数、发起人、开始与耗时。

**任务详情**:概览、进度、目标级状态、只读日志、结果(跳转漏洞页并带筛选)。操作:暂停、停止、重新扫描、导出。危险操作二次确认并说明影响。

**定时计划**:列表、启停开关、下次执行时间、历史执行记录。

**扫描方案**:预置方案只读,可"复制为自定义方案"。自定义方案只开放产品语言的选项(检测范围、强度、排除项),不暴露引擎命令行。

### 4.4 漏洞

- **列表列**:严重度、名称、资产、端口或位置、状态、首次与最近发现、来源引擎、CVE。
- **筛选**:严重度、状态、资产、业务组、时间范围、引擎、CVE 关键字。筛选条件写入 URL,方便分享。
- **详情抽屉**:描述、影响、修复建议、证据(代码块展示,敏感信息脱敏)、状态时间线、关联资产。
- **处置**:状态流转 + 备注 + 指派;支持批量操作;"重新扫描该漏洞"用于复测。
- **接受风险**必须填写原因和到期时间。

### 4.5 报告

选择范围(资产、业务组、任务、时间)和模板(总览报告、资产报告、任务报告),生成后可下载 HTML 和 CSV/JSON。PDF 放后期。报告内容与界面数据必须一致。

### 4.6 系统

- **用户与角色**:增删改、启用停用、重置密码。
- **节点管理**:Worker 在线状态、版本、最后心跳、当前任务。
- **规则库**:当前版本、更新时间、来源;导入离线包;回滚(需确认并写审计)。
- **授权范围**:提交、审批、到期。
- **审计日志**:谁、何时、做了什么;可按人和操作类型筛选。
- **系统设置**:时区、会话时长、通知(后期)。

## 5. 体验规范(每个页面都要满足)

### 5.1 状态与反馈

| 场景 | 要求 |
|---|---|
| 加载 | 使用骨架屏,不要整页转圈 |
| 空状态 | 一句话说明 + 一个主操作按钮("还没有资产,去添加") |
| 出错 | 说明原因和怎么办,附请求编号;**不用浏览器 `alert`** |
| 成功 | 右上角轻提示,不弹窗打断 |
| 危险操作 | 二次确认,写明影响范围;停止、删除、回滚、批量状态变更都算 |
| 长任务 | 显示进度,可离开页面后回来继续看 |

### 5.2 表格(通用 `DataTable` 组件统一提供)

服务端分页、排序、筛选条件持久化到 URL、列显示设置、批量选择、导出、行点击打开详情抽屉、大数据量虚拟滚动。

### 5.3 统一术语与状态

后端枚举作为唯一来源,前端用一张映射表统一文案和颜色,**页面里不得自己写状态文字和颜色**。

| 类别 | 取值 |
|---|---|
| 严重度 | critical / high / medium / low / info(中文:严重、高危、中危、低危、信息,颜色固定) |
| 任务状态 | queued、waiting_window、running、paused、completed、failed、canceled |
| 漏洞状态 | open、reopened、in_progress、fixed、false_positive、accepted_risk |

### 5.4 其他

- 中文为主,文案集中放在 i18n 文件里,预留英文。
- 桌面端(宽度 ≥ 1280)为主,平板可用。
- 所有交互元素可键盘访问,颜色对比度达标,不只靠颜色区分状态(加图标或文字)。
- 离线可用:不依赖 CDN、外部字体或外部图标。
- 页面标题、面包屑、浏览器标签标题保持一致。

## 6. 设计系统与前端工程约定

### 6.1 技术栈(沿用现有 React + Vite + Ant Design 5)

| 用途 | 选择 |
|---|---|
| 路由 | React Router |
| 数据请求与缓存 | TanStack Query |
| 图表 | ECharts |
| 国际化 | react-i18next |
| 测试 | Vitest + Testing Library;关键旅程用 Playwright |
| API 类型 | 由 OpenAPI 生成(不再手工同步) |

新增依赖需说明用途,许可证限 MIT、Apache-2.0、BSD、ISC。

### 6.2 目录约定

```text
web/src/
  app/          # 路由、布局、全局 Provider、权限守卫
  pages/        # 每个页面一个目录,只做组装
  features/     # 业务模块(assets、scans、findings、reports、system)
  components/   # 通用组件(见下)
  services/     # API 客户端、错误处理、OpenAPI 生成的类型
  hooks/
  theme/        # 设计令牌(颜色、间距、字号、圆角)
  i18n/
  utils/
```

### 6.3 必须先做的通用组件

`PageHeader`、`DataTable`、`FilterBar`、`SeverityTag`、`StatusTag`、`StatCard`、`EmptyState`、`DetailDrawer`、`DangerConfirmModal`、`QuickStartChecklist`、`ErrorState`、`LoadingSkeleton`。

### 6.4 规则

- 页面里**不写硬编码**的颜色值、状态文字、接口地址。
- 不直接用 `fetch`,统一走 `services` 里的客户端。
- 不再保留"前端 mock 模式"。演示靠后端的**种子数据**:提供 `make seed-demo` 一键导入演示数据(只用示例地址段 `192.0.2.0/24` 等)。
- 角色权限:后端强制校验,前端只负责隐藏入口。
- 令牌和会话不放 `localStorage`,使用后端设置的 HttpOnly Cookie。

## 7. 后端与 API 调整约定

### 7.1 领域划分

`assets`、`scans`(方案、计划、任务)、`findings`、`reports`、`system`(用户、节点、规则库、授权、审计)。每个领域一个目录,接口、服务、存储分层清晰。

### 7.2 API 约定

- 路径:`/api/v1/<资源复数>`,如 `/assets`、`/scan-tasks`、`/findings`。
- 列表参数:`page`、`page_size`、`sort`(如 `-last_seen_at`)、各字段筛选。
- 列表响应:`{ "items": [], "page": 1, "page_size": 20, "total": 0 }`。
- 错误响应:`{ "code": "SCOPE_VIOLATION", "message": "...", "hint": "...", "request_id": "..." }`,配错误码表 `docs/api/error-codes.md`。
- 时间一律 ISO 8601 UTC,前端按用户时区显示。
- `docs/api/openapi.yaml` 是契约,前端类型由它生成。
- 范围校验失败等安全相关错误**失败即关闭**,返回明确原因。

### 7.3 一条命令跑起来

- `sec-server` 单个程序启动即可:内嵌前端静态文件,默认使用 SQLite,自动建表。
- 首次启动自动创建管理员账号并在日志里打印一次性初始密码,首次登录强制修改。
- `make dev`:同时启动后端与前端开发服务。
- `make seed-demo`:导入演示数据。

## 8. 执行阶段(每个阶段都有"能看到的效果")

**你会看到**:总览点数字 → 进入已筛选的漏洞列表 → 打开详情 → 处置。
**验收**:总览数字与明细一致(自动化测试);筛选条件刷新页面后仍在。

### Stage 4:报告、定时计划与系统管理

- 报告生成与下载(HTML、CSV、JSON),内容与界面一致。
- 定时计划(含时间窗)、启停、历史。
- 用户与角色、节点管理、规则库(查看版本)、授权范围与审批、审计日志。

**你会看到**:完整走通旅程 3,管理员能看到节点在线和审计记录。
**验收**:无审批的范围不能发起扫描;关键操作都有审计记录。

### Stage 5:接入真实扫描引擎

- 用 Nuclei 替换假任务,扫描实验靶机;随后接入 Trivy。
- 强度档位映射到引擎参数,界面不暴露引擎命令行。

**你会看到**:真实扫描的结果出现在漏洞列表里。
**验收**:任务只连接输入的"IP:端口";结果带稳定指纹,重复扫描不重复入库。

### Stage 6:打磨

- 所有页面补齐加载态、空状态、错误态。
- 首次使用引导、页面内帮助提示、术语说明。
- 性能(大表格虚拟滚动)、可访问性、i18n 抽取。
- Playwright 覆盖三条核心旅程。

**验收**:三条旅程的端到端测试全部通过;第 5 章的体验规范逐项自检通过。

## 9. 反模式清单(Codex 做每个页面时对照)

- 一个页面塞进多个不相关功能。
- 同一个功能出现在两个菜单里。
- 在界面上暴露引擎参数、内部枚举值或数据库字段名。
- 用 `alert` 或默认的浏览器弹窗。
- 状态用纯颜色表示,没有文字或图标。
- 空白页面没有任何指引。
- 数字不能点击,或点击后没有带筛选条件。
- 为了演示而在前端伪造数据,或在接口失败时悄悄回退成假数据。
- 未实现的功能放一个菜单入口。
