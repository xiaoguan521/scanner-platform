# OrbStack 靶场功能验证方案

**状态：自定义端口端到端验证与排除端口验证已完成；V5 全 TCP 端口任务清册已显示完成，结果待逐项核验。** 已在 VPN 保持开启的情况下调整 OrbStack Docker 地址池并重启引擎；宿主机已确认可通过容器直连路由访问单个授权靶机。此方案已移除独立 TCP 探测用例；TCP 端口检查作为自动综合扫描的一部分验证。

## 1. 验证目标

在本机 OrbStack 靶场验证平台当前已实现的扫描链路：

1. 自动综合扫描只对明确登记的数字 IP 和本次授权端口做 TCP 探测与有限服务识别。
2. 通过固定主机指纹的 SSH profile 读取 Debian 系统信息和软件包清单，再由本地 Trivy 数据库做版本漏洞匹配。
3. 对授权范围内识别出的 HTTP 服务执行受限、只读的 Nuclei 检查。

这里的“自动综合扫描”是平台当前已实现的扫描组合，不代表对服务器做了全盘安全审计。SSH 使用固定只读采集器检查 OS 与包管理器数据库；不会遍历整个文件系统、审计系统配置/进程/内核、执行任意远程命令或尝试登录口令。Trivy 对已采集的软件包做本地数据库匹配，Nuclei 只检查授权 HTTP 服务。当前靶机只有 Apache 和 SSH 守护进程在运行；Tomcat、MariaDB、PostgreSQL、Redis 只安装了软件包，所以它们只会出现在软件包采集结果中，不会被识别成运行中的网络服务。

本方案不验证利用、爆破、口令猜测或通用漏洞原理验证。若目标是更完整的主机配置审计，需要另行实现并验收相应的只读 SSH 检查项；不能把当前包清单扫描描述成完整主机安全审计。

## 2. 固定验证范围与安全边界

| 项目 | 本方案取值 |
|---|---|
| V1–V4 目标 | `127.0.0.1`（单个数字 IP） |
| V5 目标 | 用户授权的单个靶机容器 IPv4，作为独立资产登记 |
| SSH | V1–V4 使用宿主机 TCP `12222`；V5 使用靶机 TCP `22` |
| HTTP | V1–V4 使用宿主机 TCP `18080`；V5 使用靶机 TCP `80` |
| 本次已验证的端口策略 | 自定义，只填 `12222,18080` |
| 靶机网络 | Compose 转发端口仅绑定 `127.0.0.1`；V5 需确认 OrbStack 容器 IP 能从宿主机直连 |

“常见端口”是预设的 69 个端口，不代表完整端口范围；若 SSH 使用自定义端口（本靶场是 `12222`），只选常见端口就可能漏掉 SSH，无法触发 SSH 软件包采集。本次已完成验证使用自定义端口 `12222,18080`，不是 69 端口预设。

全 TCP 端口 `1–65535` 需在任务页二次确认。候选服务失败处理与任务失败状态回报已修复，用户已授权仅扫描单个靶机容器 IPv4。保持 VPN 开启时调整 OrbStack Docker 地址池并重启后，宿主机路由已直达靶机容器；靶机 SSH 主机指纹和只读公钥登录已核对。V5 已按单个登记靶机、全 TCP 端口、温和强度及 Asia/Shanghai 09:00–18:00 时间窗创建，任务清册现已显示完成，扫描结果待逐项核验。

即使全 TCP 扫描成功，它也只是扩大同一目标 IP 上的端口发现范围，不会自动变成文件系统或主机配置审计。不得添加其他 IP/网段、扩大到 OrbStack 网段或尝试密码登录；SSH 仅使用靶场预置的公钥凭据。测试期间若端口不通，先修复靶场，不要扩大到其他目标来“找”目标。

## 3. 前置准备

### 3.1 检查靶机与本地平台

在仓库根目录运行：

```bash
docker compose -f lab/orbstack-target/compose.yaml ps
curl --fail http://127.0.0.1:18080/
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
```

预期：`linux-server` 为 `Up`；HTTP 返回靶场页面；平台两个健康端点均成功。若平台尚未启动，从根目录运行：

```bash
SCANNER_SSH_CONFIG=runtime/ssh/ssh-config.json make dev
```

首次访问 `http://127.0.0.1:8080` 时按页面提示创建管理员。任务列表中的 `framework-demo` 是启动合成数据，不作为靶场扫描结果。

### 3.2 检查 SSH 指纹与认证

靶机重建后先重新核对指纹：

```bash
docker compose -f lab/orbstack-target/compose.yaml exec -T linux-server \
  ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
ssh-keygen -lf runtime/ssh/scanned-host.pub
```

两条输出中的 SHA256 指纹必须一致。随后确认配置中的公钥登录可用：

```bash
ssh -T -i runtime/ssh/orbstack-target -p 12222 \
  -o BatchMode=yes -o IdentitiesOnly=yes \
  -o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile=runtime/ssh/known_hosts \
  -o GlobalKnownHostsFile=/dev/null \
  scanner_ro@127.0.0.1 'id -un'
```

预期输出为 `scanner_ro`。这只验证 SSH 连通性，不采集系统信息；正式采集由 Worker 的固定脚本执行。

### 3.3 准备扫描引擎和规则

执行扫描前确认 Nuclei、Trivy 和漏洞规则库已就绪。当前验证环境已准备好这两种引擎和规则库，不需要重新下载。注意仓库的 `make engines` 默认安装全部配置的引擎，其中包括本方案不使用的 ZAP；若重建环境并决定继续跳过 ZAP，应使用引擎安装脚本分别准备 Nuclei、Trivy，再按项目流程准备规则库，不要直接运行默认的 `make engines`。

若本地平台未运行，从仓库根目录按项目配置启动，并在“节点”页确认 Nuclei、Trivy 与规则版本均就绪；任一未就绪时先修复环境，不继续创建真实扫描任务。

| V2 | Trivy 系统包漏洞分析 | 检查 V1 的 SSH 采集状态、Trivy 引擎/规则就绪状态，以及任务发现项中的漏洞编号、安装版本和修复版本（若有）。靶机本地可用 `docker compose -f lab/orbstack-target/compose.yaml exec -T linux-server dpkg-query -W apache2 tomcat10 mariadb-server postgresql redis-server` 查看测试基线版本。 | Trivy 使用当前本地规则版本分析采集到的 Debian 软件包。结果页显示受影响组件而非完整软件包清单；CVE 命中属于版本匹配，不是利用验证。SSH 失败或未配置时必须显示未采集/失败，不能显示成“无漏洞”。 | 已完成，与 V1、V3 组成自定义端口端到端验证。 |

## 5. 如何解读结果

- **版本识别：**服务画像中的 Apache/SSH 信息来自授权端口的有限协议识别；系统包版本来自 SSH 采集的 Debian 包数据库。两种证据来源应分别核对。
- **版本漏洞匹配：**Trivy 将已采集包版本与本地漏洞数据库比对。这属于版本/公告匹配，可能受发行版回补、漏洞数据库时间和上游映射影响。
- **HTTP 基线：**Nuclei 当前使用受限只读规则检查 HTTP 响应，不等于完整 CVE 模板覆盖。
- **漏洞原理验证：**当前平台没有通用的漏洞原理验证能力；不得将版本命中或安全头提示写成“已验证可利用”。如需验证特定 CVE，应先确认平台已有对应的只读验证规则，并为该 CVE 单独选择隔离靶机。
- **未启动的中间件：**Tomcat、MariaDB、PostgreSQL、Redis 可通过系统包清单核对安装版本；本靶机没有启动它们的网络服务，因此不能用本方案声称完成这些产品的网络协议识别或运行态验证。
